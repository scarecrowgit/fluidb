# fluidb vs PostgreSQL vs ClickHouse

End-to-end comparison of fluidb (`htapd`, commit `770f8b6`) against PostgreSQL 17.11 and ClickHouse 25.8.33.
All three engines ran on one host and were driven over their own network protocols by the same Python
client, with the same SQL text. Run on 2026-09-19.

Unlike `docs/BENCHMARKS.md` (Criterion microbenchmarks of internal APIs), this measures the whole path a
user sees: wire protocol, parse/bind, execution, storage, and fsync.

## Summary

- **Answers match.** All 9 analytical queries returned the same results on all three engines at both scales.
- **Analytics are 2–4 orders of magnitude slower.** Every fluidb query costs about one full scan at
  ~1.8–2.4 µs/row: 1.7–3.7 s at 1M rows and 17–37 s at 10M. Postgres takes 1 ms–2 s and ClickHouse
  1–90 ms. Selectivity makes no difference. A 10k-row primary-key range (Q6) takes as long as `COUNT(*)`,
  so there is no PK-range pushdown on row tables. Joins cost about 2× a scan.
  *Caveat:* these are row-storage tables. SQL cannot convert a table to columnar storage (only the Rust API
  `LocalServer::convert_table_to_column` can), so the colstore path was **not** exercised here.
- **Point reads are fine at 1 client but do not scale.** fluidb serves about 2,600 selects/s at 1 client
  (p50 0.37 ms, versus 9,100/s for Postgres). It stays flat at about 3,000/s from 1 to 32 clients, while
  Postgres reaches 47,000/s, because every statement runs under `LocalServer`'s single `execution_lock`.
  ClickHouse is slower than fluidb for point lookups, as expected.
- **Writes are capped at about 70–100 commits/s, whatever the client count.** Each single-row autocommit
  `INSERT` does **6 `fsync`s and 1 `rename`** (measured with strace, see `bench/compare/diag.py`) under the
  global lock, with no group commit. Latency therefore grows linearly with clients: p99 is 0.5 s at 32
  clients. Postgres does 1,000–17,000 commits/s on the same disk.
- **Analytics block OLTP completely.** While one client loops a group-by (Q3), fluidb's OLTP throughput
  drops 94% at 1M and 99% at 10M. p99 rises to 2.6 s and 24.8 s, because each analytic query holds the
  execution lock for its whole run. Postgres loses 14% / 68%, ClickHouse 29% / 49%. This is the main gap
  for an HTAP engine.
- **Storage uses about 9× Postgres.** 10M rows take 8.9 GiB (Postgres 1.0 GiB, ClickHouse 0.2 GiB). In a
  200k-row sample, 62% of the bytes were `txn.journal` (the 2PC journal encodes payloads as JSON arrays of
  decimal bytes and is never truncated). The rest is rowstore WAL plus SSTs.
- **Two correctness surprises**, both undocumented:
  1. `INSERT` of an existing primary key silently **overwrites** the row. MySQL (and Postgres) reject it
     with a duplicate-key error. Duplicates inside one multi-row `INSERT` are rejected.
  2. `DELETE ... WHERE id = <missing>` reports 1 affected row.

## Setup

| | |
|---|---|
| Host | AMD Ryzen 5 3600 (6 cores / 12 threads), 31 GiB RAM, Linux 6.18.45, Docker 29.7 |
| Engines | cores 0–7 (`taskset` for `htapd`, `--cpuset-cpus` for containers), containers `--memory 16g`, host networking |
| Client | Python 3.12 in Docker on cores 8–11, one process per client connection (`MySQLdb` 2.3, `psycopg` 3.3 binary, `clickhouse-driver` 0.2.11 native TCP) |
| fluidb | `htapd` release build of `770f8b6` (the uncommitted working-tree changes were **not** included), `--disable-compression`, default durability (WAL `sync_on_commit = true`) |
| Postgres | `postgres:17` with `shared_buffers=4GB effective_cache_size=12GB work_mem=64MB max_parallel_workers_per_gather=4 max_wal_size=8GB`; `fsync`/`synchronous_commit` left on |
| ClickHouse | `clickhouse/clickhouse-server:25.8`, defaults; `MergeTree ORDER BY id` |
| Storage | 1M scale: Samsung PM981 NVMe. 10M scale: Kingston A400 SATA SSD (the NVMe was too full). Within a scale, all three engines were on the same device. |

**Schema.** `orders(id BIGINT PK, customer_id BIGINT, product_id INT, quantity INT, price DOUBLE,
status VARCHAR(16), region VARCHAR(16), created_ts BIGINT)` and `customers(id BIGINT PK, name, country,
segment)` with 100k rows. Timestamps are epoch-second `BIGINT`s, because fluidb's `TIMESTAMP` accepts only
numeric literals. Data is deterministic, generated by `order_row()` in `bench/compare/bench.py`.

**Workloads.**
- Load: multi-row `INSERT` in batches of 5,000 rows over a single connection. Afterwards, Postgres runs
  `VACUUM ANALYZE` and ClickHouse runs `OPTIMIZE FINAL`.
- Analytics: Q1–Q9 below, 1 warm-up run then the median of 5 runs (3 at 10M).
- OLTP: 10 s per cell at 1, 8 and 32 clients, with uniformly random keys. `point_select` is
  `SELECT * … WHERE id = ?`. `point_update` is `UPDATE … SET quantity = quantity + 1 WHERE id = ?`.
  `insert_one` is a single-row autocommit `INSERT`. `txn` is `BEGIN; SELECT; UPDATE; INSERT; COMMIT`.
  ClickHouse has no row `UPDATE` or multi-statement transactions, so those cells are n/a.
- Mixed HTAP: 8 clients doing 50/50 `point_select`/`insert_one` for 30 s, first alone, then with a 9th
  client looping Q3.

| | Query |
|---|---|
| Q1 | `SELECT COUNT(*) FROM orders` |
| Q2 | `SELECT SUM(price * quantity) FROM orders WHERE status = 'shipped'` |
| Q3 | `SELECT region, COUNT(*), SUM(price), AVG(quantity) FROM orders GROUP BY region ORDER BY region` |
| Q4 | `SELECT status, region, COUNT(*) FROM orders WHERE quantity > 5 GROUP BY status, region ORDER BY status, region` |
| Q5 | `SELECT customer_id, SUM(price) AS s FROM orders GROUP BY customer_id ORDER BY s DESC, customer_id LIMIT 10` |
| Q6 | `SELECT COUNT(*), SUM(price) FROM orders WHERE id >= N/2 AND id < N/2 + 10000` |
| Q7 | `SELECT COUNT(*) FROM orders WHERE created_ts >= a AND created_ts < a + 30 days` |
| Q8 | `SELECT COUNT(DISTINCT customer_id) FROM orders` |
| Q9 | `SELECT c.country, SUM(o.price) AS rev FROM orders o JOIN customers c ON o.customer_id = c.id GROUP BY c.country ORDER BY rev DESC` |

## Caveats

- **The columnar path was not measured.** SQL cannot convert a table to columnar storage, so every fluidb
  table stayed `Row`. A follow-up should run the analytics on converted tables through the Rust API, or
  after adding an SQL command for conversion.
- **Scales ran on different disks.** 1M ran on NVMe and 10M on a DRAM-less SATA SSD, so write numbers
  should only be compared within a scale. Postgres's writes suffered a lot on the SATA disk (for example
  `point_update` at 1 client fell from 962/s to 134/s). fluidb's commit rate was slightly *higher* there
  (about 95/s versus 70/s); that was not investigated.
- The servers had logical CPUs 0–7, which is all 6 physical cores. The client's CPUs 8–11 are SMT siblings
  of cores 2–5, so client and servers share physical cores, equally for every engine. At 32 clients the
  Python client can itself limit the fastest engines (Postgres point selects level off around 47k/s).
- Timings are single runs per cell with medians over repeats; expect ±10% noise. Postgres and ClickHouse
  run with mostly default settings, not tuned for this workload.
- ClickHouse is an analytics engine. Its point-lookup and single-row-insert numbers show that design
  trade-off, not a flaw.

## Reproducing

```bash
# 1. Build htapd from a clean checkout of the commit under test
git worktree add --detach target/compare-src HEAD
(cd target/compare-src && CARGO_TARGET_DIR=$PWD/../compare-build cargo build --release -p htapd)

# 2. Client dependencies (stock python image + a cached volume)
docker volume create fluidb-bench-pydeps
docker run --rm -v fluidb-bench-pydeps:/deps python:3.12-bookworm \
  pip install --target /deps mysqlclient pymysql "psycopg[binary]" clickhouse-driver

# 3. One scale, all three engines, all data on one device (~1 GiB per million rows for fluidb)
HTAPD=$PWD/target/compare-build/release/htapd bench/compare/run_scale.sh 1000000 /var/tmp/fluidb-compare
python3 bench/compare/summarize.py bench/compare/results.jsonl
```

`run_scale.sh` starts `htapd` and the Postgres and ClickHouse containers on the given data directory,
runs load → size → analytics → OLTP → mixed for each engine in turn, and deletes each engine's data before
starting the next. `bench/compare/diag.py` is the fsync-per-commit probe. Run it against an `htapd` started
under `strace -f -e trace=fsync,rename`.
