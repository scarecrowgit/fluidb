**Disclosed gaps.** Each table imports in independently committed batches (`LoadOptions::batch_rows` rows per commit); a failure partway through a table's import leaves its earlier batches committed, with no whole-table rollback — `load_dataset`'s own post-load check is an all-or-nothing *verification* after the fact, not an all-or-nothing *transaction*. Retrying `load_dataset` against a server root where the TPC-H tables were previously loaded, then dropped and recreated, fails with `HtapError::Conflict` from the movement job store rather than loading cleanly: each table's movement job ID is the fixed string `tpch-load-<table>`, that job store persists independently of the catalog, and table/tablet IDs are never reused, so the new load's request descriptor (carrying the new IDs) no longer matches the stale job record's — the call fails loudly rather than silently reusing or skipping data; the workaround is a fresh server root.
